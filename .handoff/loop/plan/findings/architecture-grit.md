# Findings — architecture-grit (R5)

Target: `/home/drdave/Desktop/meta/grit` (single crate v0.4.0, ~6.7k LOC). Dimension: core
architecture, data-flow, hotspots/coupling, dead-code, public-API/contracts, correctness, perf, the
lock-store abstraction, parser, git integration, the "room" concept, and **union-fitness for UNION
STEP 2** (symbol-level dedup of the ~95%-shared handoff↔rusty-idd crates).

Graph note: `graph/<T>.{symbols,callgraph,metrics}.json` were NOT produced for grit (only
`graph/target-dag.{json,md}` exist). Blast-radius below is derived from direct call-path reading, not
from a cartographer metrics file — this is a noted gap, not a fabricated graph query.

## Verdict (dimension)

grit is a **single-repo, advisory symbol-LOCK + git-worktree-MERGE coordination layer**. Its "merge"
is plain `git merge --no-ff` at the text/line level (git/mod.rs:243); its "no conflicts by design"
property comes from *partitioning* edits at symbol granularity, not from any symbol-level
reconciliation. It has the raw material for dedup (a per-symbol content hash) but **no dedup, no
cross-repo symbol identity, and no symbol-level merge operation**. As the engine for UNION STEP 2 it
is **unfit as-is**: usable only as the parallel-agent coordination substrate around a dedup process
that must be built elsewhere.

## Named gaps (vs. a dedup/union engine)

1. **No cross-repo symbol space.** Cannot represent "repo A `crates/cli::foo` ≡ repo B `crates/cli::foo`". Identity is one canonicalized root (parser/mod.rs:95).
2. **No similarity metric.** Dedup of 95%-identical crates needs structural/textual similarity scoring; grit has exact-name match + an unused exact hash only.
3. **No symbol-level merge/canonicalization.** The "merge" verb is git-branch text merge. There is no operation that takes two symbols and emits one unified symbol (or a conflict report at symbol granularity).
4. **Backend read/write skew (cloud).** Availability/plan/symbols views lie under S3/Azure.
5. **Room substrate vestigial.** Real-time eventing only works if `grit init` is kept alive; functional path is polling.
6. **Partial-claim lock leak** and **id collisions** undermine using grit as a precise symbol ledger for a union.
7. **Call-graph is over-approximate** (name-only), so `--with-deps` locking is imprecise — risky as the basis for "lock the symbol and everything it touches" during a union.

## Cross-dimension hooks (for the architect)

- **For test-coverage:** no integration test exercises S3/Azure backends or the cross-backend read-skew; add backend-parametrized tests (the read-skew bug has zero coverage).
- **For governance/config:** `grit` is NOT in the no-C trust boundary story — `rusqlite` uses `bundled` SQLite (C) and the tree-sitter grammars are C. If the union engine must live inside the envctl no-C boundary, grit's substrate choice is itself an ADR-level decision; the merge/dedup logic could be lifted out of grit into a pure-Rust component that *uses* grit only for coordination.
- **For rust-port-merge:** the harness already references "grit locks" as the symbol-level conflict-resolution mechanism (`rust-port-merge` skill). This analysis shows grit provides the *lock*, not the *merge* — the merge-integrator must supply symbol-level reconciliation itself.
